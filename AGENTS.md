# AGENTS.md

SlickBI is a closed-source, local-first desktop BI application for Windows, macOS and Linux.
People author charts and dashboards against their own data, keep their workbooks on their own
disks, and pay only for artifacts that leave their machine.

This file is the operating manual for anyone working in this repository, human or agent. It is
deliberately short. The detail lives in the documents below, and those documents are
authoritative.

If code and documentation disagree, that is a defect. Fix whichever is wrong in the same change.

Feature work is named by its ID from `FEATURES.md` (`D05`, `C02`, `X03`). Commits, tests and
issues reference those IDs so the reason for a change is never a matter of memory.

## Branch model

- `dev` is the integration branch. **All work happens here.**
- `main` is release-only. It receives merges from `dev` at release time, plus hotfixes.
- Feature branches are cut from `dev` as `feat/<feature-id>-<slug>`, for example
  `feat/c03-date-functions`, and are squashed back into `dev`.
- Fix branches are cut from `main` as `fix/<slug>`, merged to `main`, then merged back into `dev`
  so the fix is never lost to the next release.
- Release branches are cut from `dev` as `release/<version>`. Artifacts are built from there.
  After smoke testing, the release branch merges to `main` and is tagged there.

Never push a broken or partial commit to `dev` or `main`. Work in progress stays on the local
machine, in an unpushed branch or a stash.

## Commits

- Atomic: one logical change, one reason to exist. If the message needs "and", split it.
- Every commit builds and passes the test suite on its own. No "will fix in the next commit".
- Conventional commit prefix, then the feature ID where one applies:
  `feat(spec): add chart encoding types (V08)`
- No commented-out code. No `TODO` without an issue or a feature ID. No dead branches.
- Do not mix formatting-only churn with behaviour changes.

## Definition of done

A change is done when all of the following are true:

1. The behaviour is implemented and covered by unit tests.
2. An integration test exists if the change crosses one of the boundaries in `TESTING.md`.
3. `cargo xtask ci` passes locally on the final commit.
4. Documentation is updated: the feature's status in `FEATURES.md`, and any affected behaviour in
   `ARCHITECTURE.md`.
5. The changelog entry is written if the change is user-visible.
6. No new warning, no new lint allowance, no skipped or ignored test.

"The tests pass" is not the same as "it works". Assert the contract: correct numbers, correct
counts, correct error types. A test that only proves something did not error is not a test.

## Testing rules

Full detail in [`docs/TESTING.md`](docs/TESTING.md). The non-negotiables:

- Every public function in every crate has unit tests, including the error paths.
- Every subsystem boundary has an integration test, run against real components, not mocks. The
  one place mocks are acceptable is the network edge (Stripe, object storage).
- The SQL planner is tested with golden files, one directory per dialect.
- The scene is tested with golden geometry plus image comparison between the on-screen renderer
  and the export renderer. A tolerance is allowed; silent drift is not.
- A bug fix includes a test that fails before the fix. Verify it fails by reverting the fix
  locally before committing.
- Never weaken, delete or rewrite an existing test to make new code pass. If a test is wrong,
  say exactly why, with evidence, in the commit message.

## Format stability

Workbooks are people's work. They must open forever.

- The workbook format is versioned. Opening a newer format is refused with a clear message;
  it is never partially loaded.
- Any change to a serialized type requires a migration, a fixture of the old format, and a test
  that the old fixture still opens with identical semantics.
- Golden fixtures live in `crates/workbook/tests/fixtures/` and are never regenerated by hand
  to make a failing test pass.

## Security rules

- Database credentials are never written to a workbook, a log, a crash report or a test fixture.
- Credentials at rest are encrypted with an AEAD cipher and keys never sit next to the ciphertext.
  Passwords are hashed with Argon2id. These are different operations and must not be confused.
- The app makes no network request the user did not initiate. No telemetry, no update pings
  without consent, no extension downloads from DuckDB's default repository.
- Anything that runs a user's SQL from a remote request compiles it from a stored spec and
  validates it against the model. A viewer never submits raw SQL.
- Published dashboards are unlisted by default and `noindex`. Any feature that makes user data
  public requires an explicit confirmation showing exactly what will be published.

## Crate boundaries

Enforced in CI, not by convention:

- Nothing below `scene` may depend on `wgpu`, `winit` or `egui`.
- `spec`, `calc`, `model` and `planner` must not depend on `engine`.
- The application must not talk to DuckDB directly; it goes through `engine`.
- Services must not be linked into the desktop application. The desktop talks to them over HTTP.

## What not to build

The three buckets in `PRODUCT.md` are a contract, not a mood:

- **Not in v1:** hosted storage, sync, publishing, any service that keeps user content.
- **Not planned:** seats, orgs, SSO, comments, row-level security, live-query embeds that require
  us to hold credentials we did not design for.
- **Out of scope:** ETL, orchestration, warehouse modelling, catalogues, being a system of record.

If a task seems to need something in those buckets, stop and raise it before writing code.

## Release process

1. Confirm every exit criterion in `RELEASES.md` for the version is met.
2. Update versions, changelog and `FEATURES.md` statuses.
3. Cut `release/<version>` from `dev`, run `cargo xtask ci` and the packaging build.
4. Install and smoke test on macOS, Windows and Linux. Capture evidence for the release notes.
5. Merge to `main`, tag, and publish artifacts.
6. Merge `main` back into `dev` so the branches never diverge.
